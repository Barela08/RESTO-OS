# RESTO OS — Notification Delivery Architecture & Spark ₹0 Push Strategy

## 1. Dual-Channel Notification Architecture Overview

RESTO OS operates across two distinct, complementary communication pipelines:

```
[Operational Event Created] (e.g. Call Waiter, Order Placed, Dish Ready)
             |
             +---------------------------------------+
             |                                       |
             v                                       v
   [CHANNEL 1: Foreground Realtime]        [CHANNEL 2: Background Web Push]
   - Mechanism: Firestore onSnapshot       - Mechanism: Web Push (FCM HTTP v1)
   - Protocol: WebSockets / gRPC stream    - Service Worker: firebase-messaging-sw.js
   - Target: Active open tabs & screens    - Target: Handheld devices locked / in pocket
   - Cost: ₹0 / Free (Spark Included)      - Architecture: Vercel Serverless Gateway
   - Sound: Web Audio Synthesis            - Sound: System push notification chime
```

---

## 2. Channel 1: Foreground Real-Time Listeners (Firestore onSnapshot)

When staff terminals (Cash Counter PC, Waiter Handheld, Kitchen Tablet) are open and active, Cloud Firestore provides instantaneous multi-device synchronization over long-lived WebSockets.

### Role-Specific Subscriptions

1. **Kitchen Terminal (`KitchenDashboard.tsx`)**:
   ```typescript
   OrderRepository.subscribeToKitchenTickets(restaurantId, stationId, (tickets) => {
     // Identifies new tickets not previously alerted in notifiedTicketIdsRef
     if (hasFreshNew) {
       audioService.playNewOrderChime();
     }
     dbAdapter.syncFirestoreKitchenTickets(mappedTickets);
   });
   ```

2. **Waiter Handheld (`WaiterDashboard.tsx`)**:
   ```typescript
   WaiterCallRepository.subscribeToWaiterCalls(restaurantId, waiterId, (calls) => {
     // Identifies pending calls not previously announced
     if (myNewCalls.length > 0) {
       audioService.playWaiterCallBell();
       audioService.vibrate([250, 100, 250]);
       voiceAnnouncementService.announceEvent(...);
     }
     dbAdapter.syncFirestoreWaiterCalls(mappedCalls);
   });
   ```

3. **Cash Counter (`CashCounterDashboard.tsx`)**:
   ```typescript
   OrderRepository.subscribeToOrders(restaurantId, (orders) => {
     if (hasNewOrder) {
       audioService.playCounterChime();
     }
   });
   ```

4. **Customer Mobile (`CustomerLayout.tsx` & `OrderTrackingPage.tsx`)**:
   - Subscribes **only** to `orders/{orderId}` and `waiterCalls` matching `tableSessionId`.
   - Visual status badges update dynamically.
   - **Zero Audio Execution**: Customer browser never executes `audioService.playWaiterCallBell()` or `audioService.playNewOrderChime()`.

## 3. Channel 2: Background Web Push (FCM) & Spark ₹0 Boundary Strategy

### The Strict Spark ₹0 Tier Boundary
The RESTO OS project targets Firebase Spark (`resto-os-3bf6c`) with **₹0 recurring monthly cost**.
1. **Google Cloud Functions Restriction**: Deploying Firebase Cloud Functions requires the Firebase Blaze pay-as-you-go billing plan. Under Spark ₹0, Cloud Functions **cannot** be deployed.
2. **FCM HTTP v1 Security Mandate**: Modern Firebase Cloud Messaging uses the FCM HTTP v1 REST API (`https://fcm.googleapis.com/v1/projects/{projectId}/messages:send`). This API strictly requires server-side OAuth2 bearer tokens generated by signing a JWT with a Google Service Account Private Key (`private_key`).
3. **Zero Frontend Secret Exposure**: Storing Google Service Account credentials or `private_key` in client-side Vite bundles (`import.meta.env.VITE_...`) is an **extreme security vulnerability** that allows full administrative takeover of the Firebase project.

### The Solution: Vercel Serverless Function Dispatcher (`/api/notify`)
RESTO OS solves this by deploying a serverless edge endpoint `/api/notify.ts` hosted on Vercel's generous free hobby tier (100,000 free invocations/month):

```
[Device Event] ---> POST /api/notify (Vercel Serverless) ---> FCM HTTP v1 REST API ---> Device SW
                       |
                       +-- Checks process.env.FIREBASE_SERVICE_ACCOUNT_KEY (Server Secret)
                       +-- Queries active FCM tokens for targetRole from deviceRegistrations
                       +-- Signs OAuth2 JWT server-side
                       +-- Never exposes private keys to client browsers
```

#### Serverless Function Architecture (`api/notify.ts`)
- **Input Parameters**: `{ restaurantId, targetRole, title, body, eventType, tableNumber, clickAction }`.
- **Token Resolution**: Queries `deviceRegistrations` collection for documents where `restaurantId == restaurantId`, `role == targetRole`, and `isActive == true`.
- **Graceful Fallback**: If `FIREBASE_SERVICE_ACCOUNT_KEY` has not yet been provisioned in Vercel project environment variables, the endpoint safely returns `status: 'FCM_SERVER_SECRET_PENDING'` without throwing errors. Foreground Firestore listeners continue delivering 100% of events without interruption.

## 4. Background Service Worker (`public/firebase-messaging-sw.js`)

The service worker runs in the background of mobile browsers (Chrome for Android, PWA, Firefox):
```javascript
messaging.onBackgroundMessage((payload) => {
  const title = payload.notification?.title || payload.data?.title || 'RESTO OS Notification';
  const body = payload.notification?.body || payload.data?.message || 'New restaurant alert';
  const clickAction = payload.data?.clickAction || '/';

  const notificationOptions = {
    body: body,
    icon: '/icons/icon-192x192.png',
    badge: '/icons/badge-72x72.png',
    tag: payload.data?.tag || 'resto-alert',
    renotify: true,
    data: { url: clickAction, eventType: payload.data?.eventType },
  };

  return self.registration.showNotification(title, notificationOptions);
});
```

### Notification Click Routing
When a staff member taps the system notification on their lock screen:
1. `notificationclick` listener captures the tap.
2. Closes the notification banner.
3. Checks if a RESTO OS window is already open. If open, focuses and navigates to the target dashboard (e.g. `/waiter`, `/kitchen`).
4. If no window is active, opens a new window directly to the target URL.

## 5. Synthetic Web Audio & Autoplay Compliance

Rather than relying on external MP3/WAV files that can fail due to CORS, network latency, or 404s, RESTO OS utilizes the Web Audio API (`AudioContext`) to generate instant synthetic tones:

- **Waiter Call Bell**: Dual harmonic strike at C6 (1046.5 Hz) and E6 (1318.5 Hz) with exponential decay.
- **Kitchen Order Chime**: Three-tone ascending chord (C5 523 Hz -> E5 659 Hz -> G5 784 Hz).
- **Counter Cash Register Chime**: Dual-tone register bell (B5 987 Hz -> E6 1318 Hz).
- **Haptic Vibration**: `navigator.vibrate([250, 100, 250])` for pocket mobile alerts.

### Browser Autoplay Policy Solution
Browsers block synthetic audio until the user has interacted with the document. RESTO OS primes the `AudioContext` when staff enter their PIN or click the station selector (`unlockAudio()`), ensuring 100% reliable sound playback for subsequent real-time events.
